# Clause Sidecar — commons-vfs-fullrepro-001

Each entry maps a stable clause ID to the verbatim candidate-visible requirement sentence and its section anchor. IDs are not embedded in the specification body.

- **CVFS-MGR-001** — `Manager, Providers, and Resolution`: “When `VFS.getManager()` is called without an installed manager, `VFS` must lazily initialize one shared `StandardFileSystemManager` and return that instance on later calls.”
- **CVFS-MGR-002** — `Manager, Providers, and Resolution`: “When `VFS.setManager(manager)` is called, `VFS` must use that exact manager for later `getManager()` calls; when the argument is null, the next `getManager()` call must lazily create a standard manager.”
- **CVFS-MGR-003** — `Manager, Providers, and Resolution`: “When `VFS.reset()` is called, `VFS` must close the current shared manager, create a new standard manager, and return the new instance.”
- **CVFS-MGR-004** — `Manager, Providers, and Resolution`: “When `VFS.close()` is called, `VFS` must close the current shared manager and clear the shared reference; repeated close calls must leave the class usable.”
- **CVFS-MGR-005** — `Manager, Providers, and Resolution`: “When `StandardFileSystemManager.init()` completes, the manager must register the scoped schemes `file`, `ram`, `zip`, `jar`, `tar`, `gz`, `bz2`, `tgz`, and `tbz2` from built-in configuration.”
- **CVFS-MGR-006** — `Manager, Providers, and Resolution`: “When an unconfigured `DefaultFileSystemManager` is initialized, it must use `SoftRefFilesCache` and `CacheStrategy.ON_RESOLVE` unless setters supplied replacements before initialization.”
- **CVFS-MGR-007** — `Manager, Providers, and Resolution`: “If `setCacheStrategy` or `setFilesCache` is called after `DefaultFileSystemManager.init()`, then the manager must raise `FileSystemException`.”
- **CVFS-MGR-008** — `Manager, Providers, and Resolution`: “When `addProvider` receives a scheme or scheme array and a `FileProvider`, the manager must register that provider for each name and expose the names through `hasProvider()` and `getSchemes()`.”
- **CVFS-MGR-009** — `Manager, Providers, and Resolution`: “If `addProvider` receives a scheme that already has a provider, then the manager must raise `FileSystemException` instead of replacing the registration.”
- **CVFS-MGR-010** — `Manager, Providers, and Resolution`: “When `removeProvider(scheme)` removes a registration, `hasProvider(scheme)` must return false and new resolutions for that scheme must fail unless a default provider handles it.”
- **CVFS-MGR-011** — `Manager, Providers, and Resolution`: “When `getProviderCapabilities(scheme)` is called for a scoped provider, the manager must return the same operation set reported by that provider's `getCapabilities()`.”
- **CVFS-MGR-012** — `Manager, Providers, and Resolution`: “If resolution or capability lookup uses an unknown scheme with no applicable default provider, then the manager must raise `FileSystemException`.”
- **CVFS-MGR-013** — `Manager, Providers, and Resolution`: “When `resolveFile` receives an absolute URI, the manager must select the registered provider from its scheme and return a non-null `FileObject` even when the addressed resource does not exist.”
- **CVFS-MGR-014** — `Manager, Providers, and Resolution`: “When `resolveFile` receives an absolute local path or a `File`, `Path`, `URI`, or `URL` naming a local resource, the manager must return a `file`-scheme object for that physical path.”
- **CVFS-MGR-015** — `Manager, Providers, and Resolution`: “When `resolveFile` receives a relative name, the manager must resolve it against the supplied base object or file, otherwise against `getBaseFile()`.”
- **CVFS-MGR-016** — `Manager, Providers, and Resolution`: “If a relative name is resolved while no explicit or manager base exists, then the manager must raise `FileSystemException`.”
- **CVFS-MGR-017** — `Manager, Providers, and Resolution`: “When `resolveFile(name, fileSystemOptions)` is called, the manager must use those options to select or create the file system, and later relative resolutions from the result must retain the same option set.”
- **CVFS-MGR-018** — `Manager, Providers, and Resolution`: “When `closeFileSystem(fileSystem)` is called, the manager must remove that file system and its object mappings from manager-owned caches and release its resources.”
- **CVFS-NAME-001** — `Canonical Names and Hierarchy`: “The `FileName` path separator must be `/`, the root path must be `/`, and every `getPath()` result must be an absolute path beginning with `/`.”
- **CVFS-NAME-002** — `Canonical Names and Hierarchy`: “When a name contains `/`, `\`, repeated separators, `.` elements, or `..` elements, resolution must normalize separators to `/`, remove redundant elements, and preserve the root boundary.”
- **CVFS-NAME-003** — `Canonical Names and Hierarchy`: “If normalization attempts to move above the file-system root or contains an incomplete or invalid percent escape, then resolution must raise `FileSystemException`.”
- **CVFS-NAME-004** — `Canonical Names and Hierarchy`: “When a RAM URI contains a valid percent escape, resolution must decode it before projecting both `getPath()` and `getPathDecoded()`; `getURI()` must retain URI validity by percent-encoding characters that require escaping, and normalization must apply the decoded structural meaning of escaped separators or dot elements.”
- **CVFS-NAME-005** — `Canonical Names and Hierarchy`: “When `getBaseName()` is called, a non-root name must return its final decoded path element and the root must return an empty string.”
- **CVFS-NAME-006** — `Canonical Names and Hierarchy`: “When `getDepth()` is called on a RAM name, the root must return zero and every non-root name must return one plus the number of path elements because the RAM file-system name contributes one additional level.”
- **CVFS-NAME-007** — `Canonical Names and Hierarchy`: “When `getParent()` is called on a name or object, the root must return null and every non-root value must return the immediately containing path.”
- **CVFS-NAME-008** — `Canonical Names and Hierarchy`: “When `getRelativeName(other)` receives a name in the same file system, it must return a normalized relative path that resolves from the receiver back to `other`.”
- **CVFS-NAME-009** — `Canonical Names and Hierarchy`: “When `getFriendlyURI()` or `FileObject.getPublicURIString()` is called, the result must omit any password while retaining enough non-secret naming information for display.”
- **CVFS-NAME-010** — `Canonical Names and Hierarchy`: “When `NameScope.FILE_SYSTEM` is used, an absolute path must resolve from the owning file-system root and a relative path must resolve from the base name.”
- **CVFS-NAME-011** — `Canonical Names and Hierarchy`: “When `NameScope.CHILD` is used, the result must be a direct child of the base; if normalization produces the base, an ancestor, a deeper descendant, or an absolute path, then resolution must raise `FileSystemException`.”
- **CVFS-NAME-012** — `Canonical Names and Hierarchy`: “When `NameScope.DESCENDENT` is used, the result must be a strict descendant of the base; if normalization produces the base, an ancestor, or an absolute path, then resolution must raise `FileSystemException`.”
- **CVFS-NAME-013** — `Canonical Names and Hierarchy`: “When `NameScope.DESCENDENT_OR_SELF` is used, the result must be the base or one of its descendants; if normalization escapes that subtree, then resolution must raise `FileSystemException`.”
- **CVFS-NAME-014** — `Canonical Names and Hierarchy`: “When `FileName.isAncestor(argument)` is called, it must return true exactly when `argument` is a strict ancestor of the receiver; when `FileName.isDescendent(argument)` is called, it must return true exactly when `argument` is a strict descendant of the receiver; when the scoped `isDescendent(argument, nameScope)` overload is called, the same receiver-versus-argument direction must apply and `nameScope` must be evaluated by the resolution-scope rules above.”
- **CVFS-NAME-015** — `Canonical Names and Hierarchy`: “When a resolved resource does not exist, `exists()` must return false and `getType()` must return `FileType.IMAGINARY`; resolving the name alone must not create backing state.”
- **CVFS-NAME-016** — `Canonical Names and Hierarchy`: “When an existing resource is a regular file, `getType()` must return `FileType.FILE`, `isFile()` must return true, `isFolder()` must return false, and its type must report content without children.”
- **CVFS-NAME-017** — `Canonical Names and Hierarchy`: “When an existing resource is a folder, `getType()` must return `FileType.FOLDER`, `isFolder()` must return true, `isFile()` must return false, and its type must report children without data content.”
- **CVFS-NAME-018** — `Canonical Names and Hierarchy`: “When `getChild(name)` addresses an existing direct child, it must return that child; when no direct child exists, it must return null.”
- **CVFS-NAME-019** — `Canonical Names and Hierarchy`: “When `getChildren()` is called on a folder, it must return every direct child in an unordered array and must return an empty array for an empty folder.”
- **CVFS-NAME-020** — `Canonical Names and Hierarchy`: “If `getChildren()` or `getChild()` is called on a missing object or a non-folder, then the object must raise `FileSystemException`, with `FileNotFolderException` used for the non-folder case.”
- **CVFS-NAME-021** — `Canonical Names and Hierarchy`: “When a `FileSelector` traverses a tree, `FileSelectInfo.getBaseFolder()` must remain the traversal root, `getFile()` must identify the current object, and `getDepth()` must start at zero for the base.”
- **CVFS-NAME-022** — `Canonical Names and Hierarchy`: “When standard selectors are used, `SELECT_SELF` must select only depth zero, `SELECT_CHILDREN` only depth one, `SELECT_SELF_AND_CHILDREN` depths zero and one, `EXCLUDE_SELF` every positive depth, `SELECT_FILES` regular files, `SELECT_FOLDERS` folders, and `SELECT_ALL` the base plus all descendants.”
- **CVFS-NAME-023** — `Canonical Names and Hierarchy`: “When `findFiles(selector)` returns matches, it must return descendants in depthwise order with a selected child before its selected parent.”
- **CVFS-NAME-024** — `Canonical Names and Hierarchy`: “When `findFiles(selector, depthwise, selected)` is called, it must append matches to the supplied list and use deepest-first order exactly when `depthwise` is true.”
- **CVFS-CONT-001** — `Content, Mutation, and Random Access`: “When `createFile()` targets an imaginary path, the object must create missing ancestor folders and a zero-length file; when the path already denotes a file, it must leave its content unchanged.”
- **CVFS-CONT-002** — `Content, Mutation, and Random Access`: “When `createFolder()` targets an imaginary path, the object must create all missing ancestor folders; when the path already denotes a folder, it must leave the tree unchanged.”
- **CVFS-CONT-003** — `Content, Mutation, and Random Access`: “If `createFile()` targets an existing folder or `createFolder()` targets an existing file, then the object must raise `FileSystemException`.”
- **CVFS-CONT-004** — `Content, Mutation, and Random Access`: “When `copyFrom(source, selector)` is called, the destination must copy every selected source object, create missing parents, and replace conflicting destination state before copying.”
- **CVFS-CONT-005** — `Content, Mutation, and Random Access`: “When `moveTo(destination)` succeeds within a writable compatible provider, the source must become imaginary and the destination must expose the source's prior type, children, content, and supported metadata.”
- **CVFS-CONT-006** — `Content, Mutation, and Random Access`: “When `delete()` targets a missing object, it must return false; when it targets a file or empty folder, it must remove it and return true.”
- **CVFS-CONT-007** — `Content, Mutation, and Random Access`: “When `delete()` targets a non-empty RAM folder, it must return false without raising an exception and must preserve the folder and its descendants.”
- **CVFS-CONT-008** — `Content, Mutation, and Random Access`: “When `delete(selector)` or `deleteAll()` is called, it must remove selected descendants in a child-before-parent order and return the number of removed objects.”
- **CVFS-CONT-009** — `Content, Mutation, and Random Access`: “When `getContent()` is called for an imaginary file, it must return a content object whose output operations materialize the file and missing parent folders.”
- **CVFS-CONT-010** — `Content, Mutation, and Random Access`: “When `getOutputStream()` is opened without append, bytes written before close must replace prior content; when append is true, written bytes must follow prior content, including when the file is created by the append operation.”
- **CVFS-CONT-011** — `Content, Mutation, and Random Access`: “When an output stream closes, the provider must commit its bytes so `getSize()`, `getByteArray()`, `getString()`, later input streams, and other resolved objects in the same namespace observe the same content.”
- **CVFS-CONT-012** — `Content, Mutation, and Random Access`: “When several input streams are opened for one file, each stream must maintain an independent cursor and return `-1` repeatedly after reaching end of file.”
- **CVFS-CONT-013** — `Content, Mutation, and Random Access`: “While an incompatible input, output, or random-access writer is open, the content must reject conflicting access with `FileSystemException`.”
- **CVFS-CONT-014** — `Content, Mutation, and Random Access`: “When `FileContent.close()` or `FileObject.close()` is called, the object must close owned streams and commit pending changes, and later operations on the same public object must remain supported.”
- **CVFS-CONT-015** — `Content, Mutation, and Random Access`: “When `getByteArray()` is called, it must return all bytes; if the reported size exceeds `Integer.MAX_VALUE`, then it must raise `IllegalStateException`.”
- **CVFS-CONT-016** — `Content, Mutation, and Random Access`: “When `getString(charset)` is called with a `Charset` or charset name, it must decode all bytes with that charset; when the charset argument is null, it must use the JVM default charset.”
- **CVFS-CONT-017** — `Content, Mutation, and Random Access`: “When `FileContent.write()` or `FileUtil.copyContent()` copies content, it must write all source bytes to the target and the `FileContent.write()` overloads must return the transferred byte count.”
- **CVFS-CONT-018** — `Content, Mutation, and Random Access`: “When `getSize()` and `isEmpty()` are called on an existing file, size must equal the byte length and emptiness must be true exactly when size is zero.”
- **CVFS-CONT-019** — `Content, Mutation, and Random Access`: “When `setLastModifiedTime(modTime)` succeeds on a writable scoped provider, later `getLastModifiedTime()` observations must agree within `FileSystem.getLastModTimeAccuracy()`.”
- **CVFS-CONT-020** — `Content, Mutation, and Random Access`: “When attribute names are queried, matching must be case-insensitive, `getAttributeNames()` must never return null, and `getAttributes()` must return a read-only map.”
- **CVFS-CONT-021** — `Content, Mutation, and Random Access`: “If a provider does not support attributes or the resource does not exist, then attribute access must raise `FileSystemException` rather than invent values.”
- **CVFS-CONT-022** — `Content, Mutation, and Random Access`: “When `getRandomAccessContent(RandomAccessMode.READ)` is opened, reads and seeks must be supported without writes; when `READWRITE` is opened on RAM or local content, reads, writes, seeks, and `setLength()` must be supported; when `getInputStream()` is obtained from either mode, it must begin at the current position, each successful read must advance the same position reported by `getFilePointer()`, and a later `seek(pos)` must set the position for subsequent random-access operations but require a newly obtained input stream.”
- **CVFS-CONT-023** — `Content, Mutation, and Random Access`: “When random access writes past the current end or `setLength()` grows content, the provider must fill the gap with zero bytes; when `setLength()` shrinks content, bytes beyond the new length must be discarded.”
- **CVFS-CONT-024** — `Content, Mutation, and Random Access`: “If `seek(pos)` or `setLength(newLength)` receives a negative value, then random access must raise `IOException`.”
- **CVFS-CONT-025** — `Content, Mutation, and Random Access`: “When `RandomAccessMode.from` is called with one or more `java.nio.file.AccessMode` arguments, a supported argument list containing `WRITE` must return `RandomAccessMode.READWRITE`, and a supported list containing only `READ` must return `RandomAccessMode.READ`; the supported values must be limited to `AccessMode.READ` and `AccessMode.WRITE`, and the required public form must not be replaced by a `Set` or `OpenOption` overload; when `toAccessModes()` is called, `RandomAccessMode.READ` must return an `AccessMode` array containing only `READ`, while `RandomAccessMode.READWRITE` must return an `AccessMode` array containing `READ` and `WRITE`.”
- **CVFS-PROV-001** — `RAM and Local Provider Behavior`: “When `ram:///` is resolved, the RAM root must exist as a folder and deletion of that root must raise `FileSystemException`.”
- **CVFS-PROV-002** — `RAM and Local Provider Behavior`: “When two RAM names are resolved with equal `FileSystemOptions`, both objects must belong to the same file-system instance; when their options differ, they must belong to distinct RAM file systems.”
- **CVFS-PROV-003** — `RAM and Local Provider Behavior`: “When no RAM maximum is configured, `RamFileSystemConfigBuilder.getLongMaxSize()` must return `Long.MAX_VALUE`; the compatibility `getMaxSize()` must use its documented integer view.”
- **CVFS-PROV-004** — `RAM and Local Provider Behavior`: “When `setMaxSize(options, sizeInBytes)` is used, the RAM file system must limit the total bytes of all file contents to that value.”
- **CVFS-PROV-005** — `RAM and Local Provider Behavior`: “If a RAM write would make total content exceed `sizeInBytes`, then closing or committing the write must raise `FileSystemException` and the namespace must remain within the configured limit.”
- **CVFS-PROV-006** — `RAM and Local Provider Behavior`: “When RAM content is renamed, appended, randomly rewritten, truncated, copied, or deleted, the quota must track the resulting total content rather than cumulative historical writes.”
- **CVFS-PROV-007** — `RAM and Local Provider Behavior`: “When `toFileObject(File)`, `toFileObject(Path)`, an absolute local path, and an equivalent `file:` URI address the same physical path, the resulting names must identify the same local resource.”
- **CVFS-PROV-008** — `RAM and Local Provider Behavior`: “When a local `FileObject` is mutated through create, write, append, move, copy, timestamp, or delete operations, the corresponding physical file-system state must reflect the completed operation.”
- **CVFS-PROV-009** — `RAM and Local Provider Behavior`: “When external local state changes, `refresh()` must invalidate attached metadata so later existence, type, child, size, and timestamp observations reflect the physical state.”
- **CVFS-PROV-010** — `RAM and Local Provider Behavior`: “If a local operation is rejected by the host file system, then the public operation must raise `FileSystemException` or `IOException` and must not report success.”
- **CVFS-ARCH-001** — `Layered Archive Behavior`: “When a `zip`, `jar`, or `tar` URI names an archive followed by `!` and an absolute entry path, resolution must expose the archive root or addressed entry as a read-only `FileObject` hierarchy.”
- **CVFS-ARCH-002** — `Layered Archive Behavior`: “When a `tgz` or `tbz2` URI is used, resolution must behave as the corresponding `tar:gz` or `tar:bz2` composition.”
- **CVFS-ARCH-003** — `Layered Archive Behavior`: “When an archive URI contains multiple layered schemes and `!` boundaries, each layer must use the preceding entry as its backing file and the final object must expose the innermost path.”
- **CVFS-ARCH-004** — `Layered Archive Behavior`: “When a literal exclamation mark belongs to an archive or entry name, callers must encode it as `%21`, and decoded naming views must restore the literal character.”
- **CVFS-ARCH-005** — `Layered Archive Behavior`: “When an archive lacks explicit directory records, the hierarchy must still synthesize parent folders needed to expose contained entries.”
- **CVFS-ARCH-006** — `Layered Archive Behavior`: “When an archive entry is a file, its type, size, timestamp, and bytes must reflect the archive entry; when it is a folder, child listing must expose its direct entries.”
- **CVFS-ARCH-007** — `Layered Archive Behavior`: “When `getParentLayer()` is called on an archive file system, it must return the immediate backing archive `FileObject`; originating RAM and local file systems must return null.”
- **CVFS-ARCH-008** — `Layered Archive Behavior`: “When archive content is read, independent streams and sequential reads after other streams or file objects close must continue to return the stored entry bytes until the archive file system is closed.”
- **CVFS-ARCH-009** — `Layered Archive Behavior`: “When ZIP entry names are decoded without an explicit option, `ZipFileSystemConfigBuilder` must use UTF-8; when a charset is set in `FileSystemOptions`, the ZIP layer must use that charset for entry names.”
- **CVFS-ARCH-010** — `Layered Archive Behavior`: “When JAR content attributes are queried, the read-only map must combine main manifest attributes with entry attributes, with entry values taking precedence for the same public attribute name.”
- **CVFS-ARCH-011** — `Layered Archive Behavior`: “If create, output, append, random-write, attribute mutation, move, or delete is requested on an archive entry, then the operation must raise `FileSystemException`.”
- **CVFS-ARCH-012** — `Layered Archive Behavior`: “If the backing archive is missing, unreadable, malformed, or inconsistent with the selected archive scheme, then resolution or first content access must raise `FileSystemException`.”
- **CVFS-CACHE-001** — `Cache Identity and Lifecycle`: “When `DefaultFilesCache` stores an object, `getFile(fileSystem, name)` must return the stored strong reference until removal, file-system clear, or cache close.”
- **CVFS-CACHE-002** — `Cache Identity and Lifecycle`: “When `SoftRefFilesCache` or `WeakRefFilesCache` stores an object, lookup must return the same live reference while its reference remains available and must return null after collection or explicit removal.”
- **CVFS-CACHE-003** — `Cache Identity and Lifecycle`: “When `NullFilesCache` receives `putFile`, it must retain nothing; `getFile` must always return null and `putFileIfAbsent` must return false.”
- **CVFS-CACHE-004** — `Cache Identity and Lifecycle`: “When `putFileIfAbsent(object)` sees no live mapping, it must install the object and return true; when a live mapping exists, it must preserve that mapping and return false.”
- **CVFS-CACHE-005** — `Cache Identity and Lifecycle`: “When `removeFile(fileSystem, name)` is called, only that mapping must disappear; when `clear(fileSystem)` is called, every mapping for that file system must disappear; when `close()` is called, every mapping must disappear.”
- **CVFS-CACHE-006** — `Cache Identity and Lifecycle`: “While `CacheStrategy.MANUAL` is active, cached metadata must remain attached until `FileObject.refresh()` or lifecycle invalidation occurs.”
- **CVFS-CACHE-007** — `Cache Identity and Lifecycle`: “While `CacheStrategy.ON_RESOLVE` is active, an external manager or object resolution must refresh the resolved object's metadata before returning it.”
- **CVFS-CACHE-008** — `Cache Identity and Lifecycle`: “While `CacheStrategy.ON_CALL` is active, state-reading `FileObject` operations must refresh provider metadata before returning their observation.”
- **CVFS-CACHE-009** — `Cache Identity and Lifecycle`: “When equal canonical names are resolved in one file system with an object cache, the manager must reuse the cached live object according to the selected `FilesCache`; with `NullFilesCache`, repeated resolution must return distinct objects.”
- **CVFS-CACHE-010** — `Cache Identity and Lifecycle`: “When manager or file-system close occurs, open resources must be released, relevant cache mappings must be cleared, and a later standard-manager initialization must start a usable lifecycle.”
- **CVFS-ERR-001** — `Error Semantics`: “If no applicable provider exists or a scheme is already registered, then the manager must raise `FileSystemException`.”
- **CVFS-ERR-002** — `Error Semantics`: “If a name is malformed or resolves beyond its permitted root/subtree, then resolution must raise `FileSystemException`.”
- **CVFS-ERR-003** — `Error Semantics`: “If a relative name has no supplied or configured base, then the manager must raise `FileSystemException`.”
- **CVFS-ERR-004** — `Error Semantics`: “If an operation requires an existing file and the object is imaginary, then it must raise `FileNotFoundException` or `FileSystemException`.”
- **CVFS-ERR-005** — `Error Semantics`: “If child listing or lookup targets a regular file, then it must raise `FileNotFolderException`.”
- **CVFS-ERR-006** — `Error Semantics`: “If byte content is requested from a folder or another no-content type, then it must raise `FileTypeHasNoContentException` or `FileSystemException`.”
- **CVFS-ERR-007** — `Error Semantics`: “If file creation targets a folder or folder creation targets a file, then the operation must raise `FileSystemException`.”
- **CVFS-ERR-008** — `Error Semantics`: “If stream state or provider capabilities reject an access mode, then content access must raise `FileSystemException`.”
- **CVFS-ERR-009** — `Error Semantics`: “If a committed write would exceed the configured RAM maximum, then the write must raise `FileSystemException`.”
- **CVFS-ERR-010** — `Error Semantics`: “If a mutation targets a read-only archive entry, then the operation must raise `FileSystemException`.”
- **CVFS-ERR-011** — `Error Semantics`: “If a backing file is not a readable archive for the selected scheme, then resolution or content access must raise `FileSystemException`.”
- **CVFS-ERR-012** — `Error Semantics`: “If a negative seek position or length is requested, then random access must raise `IOException`.”
- **CVFS-ERR-013** — `Error Semantics`: “If `FileContent.getByteArray()` observes a size above `Integer.MAX_VALUE`, then it must raise `IllegalStateException`.”
- **CVFS-ERR-014** — `Error Semantics`: “If cache strategy or cache implementation is changed after initialization, then the manager must raise `FileSystemException`.”
- **CVFS-XVIEW-001** — `Cross-View Invariants`: “When bytes are committed through a `FileContent` output or random-access view, the same canonical object and every equivalent resolution in that file system must report matching existence, `FILE` type, size, byte array, decoded string, and input-stream content.”
- **CVFS-XVIEW-002** — `Cross-View Invariants`: “When a file or folder is created, moved, copied, or deleted, its parent `getChildren()`, selector traversal, child lookup, canonical name relations, and provider backing state must agree with the completed hierarchy.”
- **CVFS-XVIEW-003** — `Cross-View Invariants`: “When a name is resolved through manager, object-relative, file-system-relative, local `File`/`Path`, or equivalent URI entry points, all results must agree on canonical `FileName` identity, root, path, parent chain, and owning file system.”
- **CVFS-XVIEW-004** — `Cross-View Invariants`: “When equal RAM options are used, resolved objects must share one RAM namespace and quota; when options differ, neither content nor cache identity must cross between the resulting file systems.”
- **CVFS-XVIEW-005** — `Cross-View Invariants`: “When local content changes through the VFS view, physical local bytes and metadata must agree after commit; when physical state changes externally, a contract-required refresh must make the VFS projections agree.”
- **CVFS-XVIEW-006** — `Cross-View Invariants`: “When an archive entry is resolved, the layered URI, entry hierarchy, content bytes, read-only capability set, and `getParentLayer()` chain must describe the same sequence of backing archives.”
- **CVFS-XVIEW-007** — `Cross-View Invariants`: “When a JAR manifest or entry attribute is visible through `FileContent`, attribute-name lookup, the read-only attribute map, and the archive entry selected by the canonical name must agree.”
- **CVFS-XVIEW-008** — `Cross-View Invariants`: “When a cached live object is reused, its file system and canonical name must match the cache key; after removal, clear, close, or `NullFilesCache` resolution, no stale object identity must be reported as a cache hit.”
- **CVFS-XVIEW-009** — `Cross-View Invariants`: “While each `CacheStrategy` is active, manager resolution, `FileObject.refresh()`, and state-reading methods must expose metadata at the freshness boundary defined for that strategy.”
- **CVFS-XVIEW-010** — `Cross-View Invariants`: “When a manager or file system closes, its cache and resource projections must agree that resources were released, while a newly initialized manager must resolve scoped providers without inheriting closed state.”
